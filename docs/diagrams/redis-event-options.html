What happens when Discord events go through Redis?

Three possible designs, from a simple broadcast to processing that can recover after a worker restarts.

Today: Discord → the Discord.js client → event handlers inside this bot process. Redis is not currently a dependency. These are proposals, not implemented behavior.

Think of Pub/Sub as a live radio broadcast. A publisher sends an event to a named channel. Every connected subscriber listening to that channel receives it. There is no inbox for subscribers who were offline. Redis Streams adds a stored event log and tracking of unfinished work.

Vocabulary: a worker is a running program that performs work; a guild is a Discord server; an adapter converts a Discord event into plain data. A channel such as lerche:dev:events:messageCreate is a routing label, not a Discord channel.

01 / learn the model

Broadcast events to interested listeners

One bot connection publishes application events. Feature handlers subscribe to their event types; a separate observer counts activity. The same event can reach both.

Example: someone sends a TTS message

  1. Discord.js receives messageCreate. The adapter publishes a versioned event containing its ID, guild ID, channel ID, author ID and the minimum required payload.
  2. The TTS handler receives it, applies the existing permissions, settings, vote checks and usage limits, and arranges playback through the guild’s voice owner.
  3. The metrics subscriber independently increments a counter. It does not generate speech or charge tokens.

Why choose it: this is the easiest model to learn and lets separate features react independently. Initially, the feature subscriber can live in the existing bot process so it still has its Discord client.

Tradeoff: Redis adds hosting, network hops and an outage dependency even for one bot process. Adding a second identical TTS subscriber creates two executions, not shared work. Pub/Sub provides no replay, processing acknowledgement or retry queue.

Failure example: the subscriber is restarting when a message is published. That message is not spoken when it reconnects. Redis persistence settings do not turn Pub/Sub into a saved inbox.

02 / scale without speaking twice

Send each guild’s work to its owner

All supported application events still enter the bus, but action events are addressed to one owner. The two branches represent different guilds, not two copies of the same TTS job.

Example: two Discord servers speak at once

A message in guild 123 goes to lerche:dev:owner:a. A message in guild 456 goes to lerche:dev:owner:b. Each owner runs that guild’s checks and ordered speech queue. Two processes can serve different guilds without both speaking every message.

Why choose it: distribute work while keeping each guild’s playback state together. Stop and disconnect actions must reach the same owner as queued speech.

Tradeoff: Redis does not assign ownership for you. Lerche needs an ownership map, safe handover, stale-owner protection and per-guild serialization. Merely hashing guild IDs is insufficient for safe failover. Events without guild IDs, including user purchases, need a separate routing rule.

Voice detail: an owner needs the Discord shard/voice adapter for its guild, or an explicit bridge to that shard. Redis cannot transfer a live Discord.js client or voice connection. Audio still travels through Discord’s voice connection, outside these event channels.

Failure example: owner A is offline. Pub/Sub drops its events; B does not automatically recover them. Scaling and reliable delivery are separate problems. This costs more operational effort than option 1 without solving event loss.

03 / recover unfinished work

Store critical events; broadcast live updates

This is an alternative to a Pub/Sub-only requirement. It uses two Redis features: Streams for retained work and Pub/Sub for notifications that can safely be missed.

Example: an entitlement changes during a worker restart

  1. The adapter appends the event to a Stream. Successfully accepted entries remain available subject to retention and Redis persistence policy.
  2. A processor in a consumer group reads it and updates Supabase. It acknowledges the entry after successful processing.
  3. If it crashes before acknowledgement, recovery logic can reclaim pending work. Repeating the update must be safe: use stable event/entity identity, database constraints and reconciliation to prevent duplicate or stale effects.
  4. After committing, it publishes a lightweight record.updated notification. Observers refresh caches. They must also refresh on startup or by expiry if they miss the notification.

Why choose it: consequential records can recover from consumer downtime. A consumer group distributes work; separate groups can independently consume the same stored events.

Tradeoff: more code and operations: retention limits, persistence/replication configuration, pending-job recovery, bounded retries and handling repeatedly failing jobs. Stored payloads need data minimization. Streams do not recover events lost before a successful append or guarantee exactly-once external effects.

Two limits: the database commit and Pub/Sub publish are not atomic. The cache notification is deliberately best effort; use an outbox if publication must be guaranteed. Consumer groups also do not preserve per-guild completion order by themselves: speech still needs ownership and serial queues.

TTS recovery is a product decision: old speech can be disruptive. Durable TTS jobs should expire, respect stop/disconnect generations and prevent duplicate speech or usage charging. Purchase/access updates have different replay requirements from speech.

Scope and recommendation

What should “all Discord events” mean?

I suggest every supported application event enters a shared adapter: messages, interactions, guild joins/leaves, entitlement changes and subscription changes. Voice-state changes can also produce application events where needed. The event set is limited by Discord intents, permissions and events actually received.

The Discord library must still manage connection lifecycle, heartbeats, resume, caches and voice mechanics locally. Startup events and library errors need explicit policies rather than blindly being fed back into Redis. We should settle this boundary before implementation.

Slash commands: ingress sends an appropriate response or defer within Discord’s three-second deadline, then dispatches work. Results return to the ingress owner for a follow-up or response edit. Keep interaction tokens off broad channels. Some interaction types require a different acknowledgement from deferReply.

Event contract: use versioned JSON with event ID, type, timestamp, source/shard information and relevant entity IDs. Include only required payload fields. Consumers must enforce authorization; JSON does not preserve methods such as message.reply(), cached relationships or live voice state.

Access: separate development and production. Channel prefixes are naming conventions, not security controls. Use authentication, restricted Redis ACLs and private/encrypted connections; grant consumers access only to necessary channels and data.

My recommendation for Lerche

Use option 1 to learn the mechanics, but design critical production processing around option 3. Add option 2’s guild ownership when distributing voice work across processes. Supabase remains the authoritative record store. First agree which events may be dropped and what “all events” includes.
